# 全球南方稿件交换领域约定

## 基础记录原则

服务采用事件时间与接收时间分离的记录方式：

* `event_time`：调用方声明的事件发生时间（作者提交修订、伙伴签发授权、
  接收方确认等）；
* `received_time`：服务端实际落账时间（UTC）。

所有业务身份（`artifact_id` / `grant_id` / `delivery_id` /
`attachment_id` / `partner_id` / `work_id`）由调用方提供稳定标识，服务端
不生成替代键。审计记录只追加，每条事件带 `prev_hash` 与 `hash` 构成哈希链；
更正通过新事件体现（撤销、撤回、再编辑、合并），不得覆盖或删除旧记录。

## 稿件与来源图

* **原稿（original）**：新作品（work）的起点，`work_id` 即原稿标识。
* **修订（revision）**：沿同一作品链的新版本，关系 `revised_from`。
* **译稿（translation）**：另起新作品，关系 `translated_from`，语言不同。
* **节选（excerpt）**：另起新作品，关系 `excerpted_from`。
* **合并（merge）**：同一作品存在多个并发首节点时，显式提交的新版本，
  关系 `merged_with`，可有多个父本。

每个稿件节点记录作者署名（`authors`）、语境说明（`context_note`）、
正文内容哈希（`content_hash`，SHA-256）、父本列表与权利方。任一节点的
祖先链即其完整来源；译稿/节选的祖先链最终指回原稿。

## 并发修订与显式合并

多位编辑可同时基于同一版本提交修订，形成多个当前首节点（head）。分叉期间
该作品**禁止投递**。必须显式调用合并：

* 恰好两个首节点时，服务端基于共同祖先做行级三方（diff3）合并，双方改动
  不重叠则自动合并；
* 双方改动重叠（含同一位置插入不同内容）产生冲突块，或首节点超过两个时，
  调用方必须提交人工解决后的最终文本。

合并必须覆盖该作品**全部**当前首节点。

## 授权

授权（grant）按以下维度生效：

* 被授权伙伴（`grantee_partner_id`）；
* 动作：`publish` 转载、`translate` 翻译、`excerpt` 节选、`edit` 编辑、
  `sublicense` 再许可；
* 地区（`regions`）与渠道（`channels`），`*` 为通配；
* 期限：`valid_from`（含）至 `valid_until`（含），无截止时间表示长期。

授权可挂在来源图任意节点上，对其全部后继版本有效；任一授权覆盖即允许
（并集），各授权携带的保全声明（`must_preserve`）取并集。署名义务沿祖先链
汇聚：转载/再编辑时必须同时保留原稿作者与各环节贡献者署名，并声明派生关系。

持有 `sublicense` 的伙伴可向第三方再许可，但其再授权的动作、地区、渠道与
期限不得超出自身持有范围；原始权利方不受此限。

## 撤回与撤销

* **稿件撤回（withdraw）**：只追加撤回标记，阻止此后的新投递与新派生；
  来源链上任一节点撤回都会阻断后继节点的新使用。
* **授权撤销（revoke grant）**：阻止此后的新使用。

撤回与撤销都**不追溯**：已签发的投递收据作为历史凭证永久保留、仍可核验；
核验结果会分别说明“历史投递事实”与“当前是否还能继续使用所投递版本”。

## 投递与收据

* 投递按 `delivery_id` 幂等：重复提交不产生新事件、不重复计数。
* 只有作品的**唯一当前首节点**可被投递；分叉时必须先合并。
* 投递先落账为 `queued`，再调用投递器；服务重启后重放事件日志，自动续发
  待发队列。分发与状态落账在同一原子区间完成，外部投递恰好一次。
* 发送成功签发收据（receipt），含内容哈希、伙伴、地区、渠道、所依据授权、
  以及发出时刻的审计链头哈希。
* 接收方确认（ack）幂等：重复回执不增加计数、不产生新事件。

## 敏感附件

附件元数据进事件日志，二进制单独存放。每个附件有所有伙伴与可见作用域
（伙伴列表或 `*`）；非可见伙伴访问时按“不存在”处理，且无权附件不得随
投递分发。

## 核验

任何接收方可通过只读接口核验：当前版本及其指纹、与原稿的关系（完整来源链）、
署名义务、可修改范围、授权在具体地区/渠道/时间的状态，以及收据与审计哈希链。
